# 구성 설계

> 이 기록은 완성된 본문을 근거로 재구성했으며 집필 당시의 기록이 아니다. 아래 챕터
> 구성과 분리 근거는 이미 존재하는 10개 챕터를 읽고 그 배열을 설명한 것이지, 집필
> 전에 세운 설계안이 아니다. 마지막 절의 "재집필 시 바꿀 지점"만이 앞으로의 제안이다.

## 1. 자료의 한 문장 요약

도구의 책임을 구분하는 데서 시작해, Nix 셸·Conan 프로필·CMake 프로젝트를 차례로 세우고,
같은 소스에서 x86_64 실행 파일과 aarch64-musl 정적 실행 파일을 만들어 Nix가 없는 장치에서
통신까지 확인한다.

## 2. 중심 질문

이 자료는 다음 질문에 답한다.

- x86_64 개발 PC에서 어떻게 Nix가 없는 aarch64 Linux 장치에서 그대로 실행되는 Cyclone DDS C++ 프로그램을 만들고, 그 결과가 재현되는지 확인하는가?

## 3. 학습 흐름

```text
도구의 책임 경계
  -> 빌드 도구(CMake·Make) 기초
  -> 환경 고정(Nix Flake)
  -> 의존성 고정(Conan recipe·프로필)
  -> 프로젝트 구조(CMake target)
  -> 애플리케이션 영역(DDS·IDL)
  -> 네이티브 빌드·실행으로 1차 검증
  -> 교차 빌드·ELF 검사로 2차 검증
  -> 배포·LAN 통신으로 3차 검증
  -> 실패 계층 분류와 완료 점검
```

큰 축은 "개념 → 환경 → 의존성 → 구조 → 도메인 → 검증 3단계 → 진단"이다. 검증을 세 번
나누어 배치한 것이 이 책 구성의 중심이다. 네이티브 실행, ELF 검사, 장치 간 통신은 각각
다른 종류의 실패를 잡아내므로 한 챕터로 합치지 않는다.

## 4. 챕터 구조

각 챕터는 개념 단위 하나를 담는다.

| 번호 | 챕터 파일 | 개념 단위 하나 | 목적 | 필요한 선행개념 | 산출되는 이해 |
|---|---|---|---|---|---|
| 1 | `01-toolchain-mental-model.md` | 누가 무엇을 소유하는가 | 네 도구의 책임과 build/host를 구분한다. | C++ 소스와 실행 파일 | 컴파일·링크 구분, 두 자물쇠(`flake.lock`·Conan lockfile) |
| 2 | `02-cmake-and-make.md` | CMake는 생성기, Make는 실행기 | configure와 build를 분리해 본다. | 1장의 책임 구분 | out-of-source build, target 기반 링크 |
| 3 | `03-nix-development-shell.md` | Flake가 도구를 고정한다 | 두 컴파일러를 한 셸에 둔다. | 2장의 CMake·Make 실행 경험 | Flake 입력 두 개, 환경 변수로 전달하는 도구 경로 |
| 4 | `04-conan-profiles.md` | recipe는 무엇을, 프로필은 어떤 환경으로 | build/host 프로필을 작성한다. | 3장의 환경 변수 | 세 프로필, platform tool, 정적 옵션, lockfile |
| 5 | `05-cmake-project.md` | Conan target을 CMake에 잇는다 | 프로젝트의 링크 관계를 완성한다. | 2장 target, 4장 generator | `find_package(... CONFIG)`, imported target 전이 |
| 6 | `06-dds-and-idl.md` | DDS는 브로커가 없다 | 만들려는 프로그램이 무엇인지 이해한다. | 5장까지의 빌드 구조 | domain·topic·자료형 일치 조건, IDL 생성물의 위치 |
| 7 | `07-native-build.md` | 같은 플랫폼에서 먼저 동작시킨다 | 네이티브로 1차 검증한다. | 3~6장 전부 | lockfile → install → configure → build → 통신 |
| 8 | `08-cross-build.md` | host만 바꾸면 결과가 바뀐다 | 교차 빌드로 2차 검증한다. | 7장의 성공 경로 | host 프로필 교체, 정적 ELF 검사 기준 |
| 9 | `09-deploy-and-network.md` | 빌드 성공은 배포 성공이 아니다 | 장치와 LAN에서 3차 검증한다. | 8장의 산출물 | 두 파일만 배포, discovery 좁히기 순서 |
| 10 | `10-troubleshooting.md` | 실패한 계층부터 본다 | 진단 순서와 완료 기준을 준다. | 1~9장 전부 | 증상별 점검표, lockfile 갱신 원칙, 최종 체크리스트 |

## 5. 챕터 분리 근거

- **1장과 2장을 나눈 이유**: 1장은 "왜 도구가 넷인가"라는 정신 모형이고, 2장은 그중 두 개(CMake·Make)의 실제 조작이다. 개념과 조작을 한 챕터에 넣으면 첫 챕터가 명령 실습으로 변질되고, 뒤에서 반복될 build/host 구분이 묻힌다.
- **2장을 3장보다 앞에 둔 이유**: 3장의 Flake가 "CMake 3.31을 별도 입력에서 가져온다"를 설명하려면 독자가 이미 CMake를 실행해 본 상태여야 한다. 도구를 모르면 버전 제약이 왜 문제인지 실감하지 못한다.
- **3장과 4장을 나눈 이유**: 고정 대상이 다르다. 3장은 도구(컴파일러·CMake·Make·Conan)를, 4장은 C++ 라이브러리를 고정한다. 1장의 "두 자물쇠"가 그대로 두 챕터가 된다. 한 챕터로 합치면 `flake.lock`과 Conan lockfile을 같은 것으로 오해하기 쉽다.
- **4장과 5장을 나눈 이유**: 4장은 Conan 쪽 선언(recipe·프로필·옵션), 5장은 CMake 쪽 소비(`find_package`·target)다. 경계가 `conan_toolchain.cmake`이고, 이 경계를 챕터 경계로 삼아야 configure 실패 시 어느 쪽 문제인지 독자가 구분한다.
- **6장을 빌드 챕터들 사이에 둔 이유**: 6장은 유일하게 도구가 아니라 애플리케이션 도메인을 다룬다. 5장까지로 "무엇을 빌드할 구조인가"가 끝나고, 7장부터는 실제 실행이므로 실행 직전에 "무엇이 실행되는가"를 넣는다. IDL 생성물을 저장소에 기록하는 이유가 8장의 `Exec format error` 회피와 직결되어, 7장 이전에 반드시 놓여야 한다.
- **7장·8장·9장을 셋으로 나눈 이유**: 검증의 성격이 다르다. 7장은 코드와 의존성이 맞는지(같은 플랫폼에서 실행해 확인), 8장은 교차 도구 체인과 정적 링크가 맞는지(실행하지 않고 ELF로 확인), 9장은 배포와 네트워크가 맞는지(다른 장치에서 확인)를 본다. 합치면 실패 시 어느 층을 의심할지 알 수 없게 되고, 이는 10장의 계층 진단 원칙과도 어긋난다.
- **10장을 별도로 둔 이유**: 앞 아홉 챕터의 실패 모드를 한 표로 모으고 인수 기준을 제공하는 참조용 챕터다. 각 챕터에 흩어 두면 독자가 문제를 만났을 때 찾아갈 단일 지점이 없다.

## 6. 읽기 순서의 의존 관계

```text
1 ──> 2 ──> 3 ──> 4 ──> 5 ──┐
                 │          ├──> 7 ──> 8 ──> 9 ──> 10
                 └──> 6 ────┘
```

- 1 → 2: 컴파일·링크 구분이 있어야 configure/build 분리가 의미를 가진다.
- 2 → 3: CMake 버전 제약을 이해하려면 CMake 실행 경험이 필요하다.
- 3 → 4: 프로필이 읽는 `AARCH64_CXX`, `CMAKE_PLATFORM_VERSION` 등을 Flake가 먼저 내보내야 한다.
- 4 → 5: `CMakeDeps`가 만든 package config가 있어야 `find_package(... CONFIG)`가 성립한다.
- 2 → 5: `telemetry_type` target과 `PUBLIC` 전이 규칙이 2장에서 먼저 소개된다.
- 6은 3·4·5와 독립적으로 읽을 수 있으나 7 이전에 읽어야 한다. 실행 인자와 QoS, 실행 순서를 모르면 7장의 통신 확인을 해석할 수 없다.
- 7 → 8: 8장은 "host 프로필만 바뀐다"로 서술되므로 네이티브 성공 경로가 기준선이다.
- 8 → 9: 9장이 배포하는 대상은 8장이 만든 정적 ELF다.
- 10은 1~9 전체를 전제하며, 문제 발생 시 언제든 되돌아오는 참조 챕터다.

## 8. 예제 계획

예제는 `assets/cyclonedds-cross-demo/` 하나다. 특정 챕터에 귀속되지 않고 여러 챕터가
같은 프로젝트를 점진적으로 완성·실행하므로 `<project-slug>` 폴더로 둔다. `index.md`는
독자가 설명을 읽으며 직접 파일을 만들거나 예제를 별도 작업 디렉터리에 복사하도록 안내한다.

| 챕터 | 사용하는 예제 파일 | 사용 방식 | 기대 결과 |
|---|---|---|---|
| 1 | 없음(구조만 언급) | `index.md`의 프로젝트 트리로 전체 모습을 보여준다. | 만들 것의 윤곽 파악 |
| 2 | `CMakeLists.txt` 발췌 | target 선언을 읽는다. | `make ... help`에 세 target이 보인다. |
| 3 | `flake.nix`, `flake.lock` | 링크로 참조하고 입력·환경 변수를 설명한다. | `nix develop` 진입과 버전 출력 |
| 4 | `conanfile.py`, `profiles/build-x86_64`, `profiles/host-x86_64`, `profiles/host-aarch64-musl`, `conan-*.lock` | 링크로 참조하고 프로필 항목을 발췌해 설명한다. | `conan graph info`에 platform CMake와 aarch64 setting이 보인다. |
| 5 | `CMakeLists.txt` 전체 흐름 | `find_package`, `telemetry_type`, `add_demo_executable`을 순서대로 읽는다. | configure 로그에 두 Conan target 선언이 보인다. |
| 6 | `idl/Telemetry.idl`, `generated/Telemetry.*`, `src/publisher.cpp`, `src/subscriber.cpp` | IDL 정의와 C++ 핵심 부분을 발췌한다. | 자료형·topic·domain 일치 조건 이해 |
| 7 | 프로젝트 전체 | 실제 명령을 순서대로 실행한다. `build/native/`에 결과를 만든다. | subscriber가 `received all 10 samples` 출력 |
| 8 | 프로젝트 전체 | host 프로필만 바꿔 `build/aarch64/`에 결과를 만든다. | `Machine`이 `AArch64`, `INTERP`·`NEEDED` 없음 |
| 9 | `build/aarch64/app/`의 두 실행 파일 | 장치로 복사해 실행한다. | 장치 내부·LAN 양방향 통신 |
| 10 | `conanfile.py`, lockfile 2종 | 갱신 절차의 대상으로 참조한다. | 최종 체크리스트 10항목 통과 |

예제 프로젝트는 `README.md`를 자체적으로 가지며, 7장과 9장의 명령은 모두 이 디렉터리를
작업 기준으로 삼는다. `generated/`는 x86_64 `idlc`로 만들어 저장소에 함께 기록하고,
`.conan2/`와 `build/`는 생성 가능한 상태이므로 기록하지 않는다.

## 9. 그림, 표, 코드 계획

- 그림: 이미지 파일을 사용하지 않는다. `text` 코드 블록의 ASCII 흐름도로 대체한다. 주요 흐름도는 `index.md`의 전체 흐름, 1.1의 컴파일·링크, 6.1의 DDS 개체, 6.3의 IDL 생성 흐름, 10.1의 실패 계층이다.
- 표: 도구 책임 표(`index.md`), 플랫폼 세 이름(1.3), 개발 셸 환경 변수(3.3), 프로필 세 개(4.3), ELF 판정 기준(8.4), 증상별 점검표(10.2)가 핵심이다.
- 코드: 모든 블록에 언어 식별자를 붙이고, 실행 명령은 `console` 블록에 프롬프트(`$`, `target$`)로 실행 위치를 구분한다.
- 검증 필요: 버전 의존 주장(CMake 4 vs `cmake/[>=3.16 <4]`), `readelf` 출력 판정, `CYCLONEDDS_URI` 문법은 `05_review.md`에서 실행 대조 대상이다.

## 10. 위험 구간

- 설명이 어려운 부분: Conan의 build/host 프로필이 왜 두 개인지. 1.3에서 이름을 세 개로 나눠 정의하고 4.3에서 표로, 8.1에서 실제 명령으로 세 번 반복한다.
- 오해가 잦은 부분: `host`를 "빌드를 실행하는 PC"로 읽는 것. `index.md`와 8.1에서 굵은 글씨로 두 번 교정한다.
- 추가 그림이 필요한 부분: 없음. 텍스트 흐름도로 충분하다.
- 예제 없이 설명하면 위험한 부분: IDL 생성물의 저장소 기록(6.3), 정적 링크 판정(8.4), discovery 실패 좁히기(9.5). 모두 실행 가능한 명령과 기대 출력을 함께 둔다.

## 12. 재집필 시 바꿀 지점

현재 본문을 읽고 판단한, 구성을 다르게 가는 편이 나을 지점이다. 본문 수정은 이 기록의
범위 밖이며, 아래는 재집필 단계에서 검토할 후보다.

1. **2장과 5장의 중복**: `add_library(telemetry_type ...)`, `target_include_directories`,
   `target_link_libraries`가 2.4와 5.2에 거의 같은 코드로 두 번 나온다. 2장은 CMake 개념을
   설명하는 자리이므로 예제와 무관한 최소 코드로 바꾸고, 실제 프로젝트 코드는 5장에서만
   제시하는 편이 낫다. 지금은 독자가 2장에서 이미 프로젝트를 다 본 뒤 5장에서 같은 것을
   다시 읽는다.
2. **lockfile 생성 절차의 중복**: 4.7과 7.2, 8.1에 `conan lock create`가 세 번 나온다.
   4.7을 "lockfile이 무엇을 고정하는가"라는 개념 설명으로 줄이고 실제 생성 명령은
   7장·8장의 실행 절차에만 두는 편이 낫다.
3. **CMake 3.x 고정 이유의 중복**: 3.1과 10.3이 사실상 같은 내용이다. 10.3은 진단 관점의
   짧은 참조로 줄이고 3.1을 유일한 설명 위치로 삼는다.
4. **musl 선택 근거의 분산**: 1.4와 8.5가 같은 주제를 다른 깊이로 다룬다. 1.4는 "왜 정적
   musl인가"만 남기고, "정적이 보장하는 것과 보장하지 않는 것"은 8.5로 모은다.
5. **6장의 위치**: 6장은 도구 사슬과 독립적인 도메인 챕터인데 5장과 7장 사이에 끼어 있어,
   3~5장의 빌드 환경 구축 흐름을 한 번 끊는다. 2장 뒤(빌드 개념 직후, 환경 구축 전)에
   두면 "무엇을 만들 것인가"를 먼저 보여준 뒤 환경을 세우는 흐름이 된다. 다만 6.3의 IDL
   생성물 기록 근거가 교차 빌드 맥락을 필요로 하므로, 옮긴다면 그 부분만 8장으로 분리해야
   한다. 두 안의 장단이 갈리므로 재집필 시 명시적으로 결정할 지점이다.
6. **확인 활동 이름의 불일치**: 1·2·4장은 "직접 확인", 3·5·6·7·8·9장은 "연습문제",
   10장은 없다. 한 책 안에서 같은 역할의 절은 같은 이름을 쓰도록 통일한다. 10장에도
   짧은 진단 연습을 하나 두면 구성이 고르다.
7. **`index.md` 읽기 순서의 제목과 챕터 H1 불일치**: `index.md`는 6장을
   "DDS, IDL, publisher/subscriber", 9장을 "대상 배포와 장치 간 통신"으로 부르는데 챕터
   H1은 각각 "DDS와 IDL 이해하기", "target 배포와 LAN 통신"이다. 목차와 제목이 다르면
   독자가 같은 챕터를 두 이름으로 기억한다.
8. **`target`의 두 가지 의미**: CMake의 target(빌드 단위)과 배포 대상 장치를 모두
   `target`으로 부른다. 9장은 제목부터 본문까지 장치를 `target`으로 표기하고 있어 2장·5장의
   CMake target과 충돌한다. 장치는 "대상 장치"로 통일하고 `target`은 CMake 용어로만
   남기는 편이 낫다.
9. **publisher/subscriber 소스의 노출 범위**: 6장은 핵심 호출만 발췌하고 전체 소스는
   예제 파일에만 있다. 인자 순서(샘플 수, 간격, domain ID, source 이름)는 7장에서야
   처음 설명된다. 6장에서 두 프로그램의 명령행 인터페이스를 먼저 정리하면 7장의 실행
   명령이 설명 없이 읽힌다.
