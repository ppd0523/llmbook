# 초고: 새 워크트리에서 개발환경을 빨리 준비하기

작성일: 2026-09-26. 이 글은 여섯 챕터로 나눌 설명 흐름의 초고이며, 최종 본문은 책 폴더의 챕터 파일에 둔다.

## 1. 새 작업 폴더가 비어 보이는 이유

에이전트 세 명에게 같은 저장소의 다른 문제를 맡기면 Orca는 작업별 Git worktree를 만든다. 세 작업은 Git 객체와 ref를 공유하지만 작업 파일과 HEAD가 다르다. 원래 작업 폴더의 `.venv`와 `node_modules`는 Git에서 제외된 설치 결과이므로 새 워크트리에 없다. 이를 곧바로 "패키지 세 번 다운로드"라고 해석하면 해결책을 잘못 고른다. 다운로드 캐시는 사용자 홈에 남아 있을 수 있고, 새 폴더가 요구하는 것은 캐시에서 설치 결과를 구성하는 작업일 수 있다.

작업 단위로 구분할 것은 네 가지다. Git 추적 파일인 잠금 파일은 브랜치마다 달라질 수 있다. Python과 Node 런타임은 사용자별로 설치되어 재사용할 수 있다. `uv`와 npm의 다운로드 캐시도 사용자별로 재사용된다. `.venv`와 `node_modules`는 워크트리별로 준비한다. 이 구분을 경로 표와 두 워크트리의 `git status --short`, `uv cache dir`, `npm config get cache` 출력으로 확인한다.

## 2. 예제를 두 개의 저장소로 준비한다

Python 예제는 `.python-version`의 `3.14`, `pyproject.toml`, `uv.lock`, `main.py`로 구성한다. `uv sync --locked` 뒤 `uv run --locked python main.py`를 실행하면 Rich 버전이 출력된다. Node 예제는 `.nvmrc`의 `24`, `package.json`, `package-lock.json`, `index.mjs`로 구성한다. `nvm use 24`, `npm ci`, `npm start`로 실행한다. 두 폴더는 책의 `assets/`에서 별도 위치로 복사한 뒤 각각 `git init`과 첫 commit을 한다. 예제 폴더 안에 이미 준비된 잠금 파일을 Git에 포함하고 `.venv`, `node_modules`는 포함하지 않는다.

버전 파일의 `3.14`와 `24`는 계열 요청이다. 패치 버전은 독자의 설치 시점에 달라질 수 있다. 그래서 실행 기록에는 `uv run python --version`, `node --version`, `uv --version`, `npm --version`, Orca 버전을 함께 적는다. 잠금 파일은 패키지 버전을 고정하지만 런타임의 패치 버전까지 고정하지는 않는다.

## 3. Python은 환경을 분리하고 캐시를 재사용한다

`uv` 프로젝트는 기본적으로 루트의 `.venv`에 설치한다. 새 워크트리에서 `uv sync --locked`를 실행하면 각자 `.venv`가 생긴다. 두 환경의 경로는 다르지만 캐시 경로는 같을 수 있다. 같은 파일시스템에 있으면 uv는 macOS에서 캐시 파일을 Copy-on-Write로 가져오는 것이 기본이다. 다운로드 시간과 환경 구성 시간을 따로 재야 이득을 확인할 수 있다.

동일한 잠금 파일의 두 브랜치에서 `uv sync --locked --offline`이 모두 성공하면 그 실행에 필요한 패키지는 로컬에서 공급되었다. 한쪽 브랜치에서 `uv add "rich==15.0.0"`으로 잠금 파일을 바꾸면 다른 쪽은 여전히 `14.3.3`을 요구한다. 두 `.venv`가 분리되어 있어야 둘을 동시에 실행할 수 있다. `.venv`를 공유 심볼릭 링크로 연결하면 `uv sync`의 정확한 동기화가 다른 작업의 설치 상태를 바꾸고, editable 패키지의 소스 경로도 잘못될 수 있다. Python 가상환경의 실행 스크립트에는 절대 경로가 들어가므로 복사도 기본 해결책으로 삼지 않는다.

## 4. Node는 nvm의 런타임과 npm 설치 결과를 구분한다

`nvm`은 셸에서 Node v24를 선택한다. Node 설치 경로는 사용자별로 공유되지만 `node_modules`는 새 워크트리에 없다. `npm ci`는 `package-lock.json`에 맞춰 새 폴더를 만들며, 기존 `node_modules`가 있으면 먼저 지운다. npm 캐시가 따뜻해 `npm ci --offline`이 성공해도 설치는 반복된다. 그러므로 오프라인 성공과 준비 시간 단축을 같은 주장으로 쓰지 않는다.

Orca setup hook이 비대화식 셸에서 실행되면 대화형 터미널의 `nvm` 함수를 그대로 사용할 수 있다고 가정하지 않는다. hook의 작업 디렉터리와 `command -v nvm`을 확인하고, 필요하면 그 셸에서 `nvm.sh`를 명시적으로 불러온 뒤 `nvm use 24`와 `npm ci`를 실행한다. `fnm`은 `.nvmrc`를 읽을 수 있지만 디렉터리 탐색과 자동 전환 설정이 nvm과 같지 않다. fnm은 비교표로만 다룬다.

## 5. Orca에서 병렬 작업과 브랜치 차이를 검증한다

두 예제를 Orca에 저장소로 등록하고, 각각 Settings → Repository → Hooks에 준비 명령을 둔다. Git ref가 준비된 뒤 같은 시작점에서 작업별 브랜치를 갖는 워크트리 여러 개를 만든다. 에이전트에게는 작업 경로, 브랜치, 잠금 파일, 실행할 검증 명령을 함께 전달한다. 하나의 워크트리를 두 에이전트에게 동시에 수정하게 하면 환경 분리의 이점도 사라진다.

첫 실험은 잠금 파일이 같은 두 워크트리의 캐시 재사용이다. 두 번째 실험은 한쪽에서 Python Rich 버전을 바꾸고 Node에는 새 의존성을 더한 뒤, 반대쪽 작업이 원래 잠금 파일과 설치 결과를 유지하는지 확인한다. 다른 브랜치의 패키지가 보이면 `pwd`, `git rev-parse --show-toplevel`, `test -L .venv`, `test -L node_modules`, 캐시·설치 경로를 조사한다.

Orca Shared Paths는 macOS에서 가능한 경우 APFS 복제본을 만들지만 그렇지 않으면 심볼릭 링크로 연결할 수 있다. 복제 여부를 확인하지 않은 공유는 별도 환경을 보장하지 않는다. 특히 `npm ci`는 기존 `node_modules`를 지우므로 복사해 둔 모듈 디렉터리가 준비 시간 단축으로 곧바로 이어지지 않는다. 기본 실습은 Shared Paths에 두 경로를 넣지 않는다.

## 6. 시간과 실패 위치를 측정한다

새 작업의 경과 시간을 `/usr/bin/time -p`로 기록한다. 첫 설치, 같은 잠금 파일의 다음 워크트리, 변경된 잠금 파일 브랜치를 구별한다. `uv sync --locked --offline`과 `npm ci --offline`을 통해 패키지 관리자 호출의 네트워크 의존성을 확인한다. 오프라인 실패는 캐시 누락 또는 런타임 준비 문제를 뜻할 수 있으므로 로그를 읽고 어느 패키지에서 실패했는지 찾는다. npm 설치 스크립트가 자체 네트워크 요청을 하는 프로젝트라면 별도로 확인한다.

느린 원인을 찾을 때는 캐시 위치와 파일시스템을 먼저 본다. `uv` 캐시와 `.venv`가 다른 파일시스템이면 빠른 링크 방식이 동작하지 않을 수 있다. `npm ci`의 반복 시간은 캐시가 있어도 남는다. hook이 프로젝트 루트가 아닌 곳에서 실행되거나 `nvm`이 로드되지 않으면 설치 명령 이전에 실패한다. 작업을 마치면 Orca diff와 미병합 브랜치를 확인하고 Orca에서 워크트리를 정리한다.

## 독자가 직접 해결할 문제

1. 세 워크트리 중 하나만 새 Python 의존성이 필요하다. 어떤 파일과 경로가 달라져야 하며 공통으로 남아도 되는 경로는 무엇인가?
2. `npm ci --offline`이 성공하지만 12초가 걸린다. 이것을 재다운로드로 판단할 수 있는가? 다음에 어떤 시간을 따로 측정할 것인가?
3. Orca hook의 `nvm use 24`가 `command not found`로 실패한다. 대화형 셸과 hook의 차이를 어떤 명령으로 확인하고 어떻게 복구할 것인가?
4. 한 브랜치에서 `rich`를 올린 뒤 다른 브랜치의 실행 결과도 바뀌었다. Git ref, 작업 경로, `.venv` 링크, 잠금 파일 가운데 무엇부터 확인할 것인가?

## 초고 점검

- 독자에게 새 용어를 경로·명령 결과와 함께 제시했다.
- 여섯 챕터가 하나의 중심 질문으로 이어지고 각 목표에 실습·문제가 대응한다.
- 최종 집필에서 Orca hook의 실제 셸·시작 디렉터리는 설치 버전으로 확인한 범위만 적는다.

## 후속 초고 보강: Git 무시 로컬 파일

패키지 설치 결과와 별도로 `.env`와 개인 도구 스크립트도 새 워크트리에 없다. 팀 공통 빌드·테스트 명령과 hook 진입점은 추적하고, 작업별로 변경할 로컬 파일은 Orca `.worktreeinclude`의 복사를 검토한다. Shared Paths는 심볼릭 링크가 될 수 있으므로 독립 편집이 필요한 파일에 사용하지 않는다. 복사된 `.env`는 실행 명령이 명시적으로 읽어야 하며 실제 비밀값은 예제에 넣지 않는다.
