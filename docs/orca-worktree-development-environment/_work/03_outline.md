# 구성 설계

작성일: 2026-09-26

## 중심 질문과 학습 흐름

Orca의 병렬 Git worktree에서 Python·Node.js 개발환경을 빠르게 준비하고 브랜치별 의존성을 안전하게 검증하는 방법을 다룬다.

```text
작업 파일 분리 → 런타임·다운로드 캐시·설치 결과 구분 → 예제 준비
→ uv와 npm의 재구성 비용 측정 → Orca setup hook 자동화
→ 병렬 브랜치 변경과 공유 경로 실패 분석 → 진단·정리
```

## 챕터와 검증 가능한 결과

| 챕터 | 중심 질문 | 핵심 개념 | 독자가 수행할 실습·확인 |
|---|---|---|---|
| 01 작업 공간과 캐시 | 같은 저장소인데 새 작업 폴더에 의존성이 없는 이유는? | Git 공통 저장소, 작업별 파일, 사용자별 런타임·다운로드 캐시, 작업별 설치 결과 | 경로·브랜치·잠금 파일·캐시 위치를 구분하는 표 작성 |
| 02 두 예제 준비 | 잠금 파일과 버전 요청을 어떻게 준비하는가? | `.python-version`, `uv.lock`, `.nvmrc`, `package-lock.json`, Git 초기 커밋 | 독립된 두 예제를 복사해 실행하고 Git 저장소로 초기화 |
| 03 Python과 uv | 두 워크트리가 설치 파일을 공유하지 않아도 어떻게 빨리 준비되는가? | uv cache, `.venv`, CoW, `--locked`, `--offline`, editable 경로 | 새 워크트리에서 동기화·실행·오프라인 재현, 환경 경로 확인 |
| 04 Node.js와 nvm·npm | Node는 있는데 `node_modules`가 없는 이유는? | 셸별 nvm 선택, npm cache, `npm ci`, 설치 스크립트 | 새 워크트리에서 `nvm use 24`, `npm ci`, 오프라인 실행; 비대화식 셸 점검 |
| 05 Orca 병렬 작업 | 에이전트 3~5개가 같은 시작점과 다른 잠금 파일로 일할 때 무엇이 충돌하는가? | Orca hook, 별도 브랜치, 변경된 lockfile, Shared Paths의 clone·symlink | 두 저장소에 hook 설정, 병렬 워크트리 생성, 한 브랜치의 의존성 변경, 공유 경로 판단 |
| 06 측정·진단·정리 | 새 워크트리 준비 시간이 왜 줄지 않는지 어떻게 알아내는가? | warm cache, 캐시 경로, 파일시스템, hook 실패, fnm 차이, 자원 정리 | 시간과 경로를 기록하고 원인별 조치 선택, 작업 결과 확인 후 Orca 워크트리 정리 |

## 개념 도입 순서

| 개념 | 첫 등장 | 설명 방식 |
|---|---|---|
| Git worktree | 01 | 같은 Git 객체 저장소를 쓰되 작업 파일·HEAD·index를 분리한 디렉터리로 정의하고 일반 branch 전환과 비교 |
| 다운로드 캐시 | 01 | 패키지 원본·압축본을 다시 받지 않도록 보관한 사용자별 데이터로 정의 |
| 설치 결과 | 01 | Python `.venv`와 Node `node_modules`로 예시; 캐시와 다름을 경로 표로 표시 |
| 잠금 파일 | 02 | 브랜치가 선택한 구체적 패키지 버전의 기록으로 설명 |
| Copy-on-Write | 03 | 복제 직후 데이터를 공유하고 쓰기 시 분리하는 파일시스템 동작으로 짧게 설명; 보장 조건 표시 |
| 비대화식 셸 | 04 | 대화형 셸 시작 파일을 자동으로 읽지 않을 수 있는 hook 실행 맥락으로 설명 |
| Orca Shared Paths | 05 | APFS 복제와 심볼릭 링크 대체 경로를 비교; `.venv`·`node_modules` 기본 실습에 사용하지 않음 |

## 예제·연습 대응

| 학습 목표 | 예제 | 직접 풀 문제 |
|---|---|---|
| 환경 준비 | Python·Node 각각 `uv sync --locked`·`npm ci` | 새 워크트리에서 누락된 파일과 재생성할 파일을 분류 |
| 병렬 브랜치 검증 | 동일 잠금 파일 두 워크트리, 한쪽만 의존성 변경 | 다른 쪽에 새 패키지가 보이면 어떤 경로 공유를 의심할지 판단 |
| 성능 진단 | 첫 실행과 따뜻한 캐시 실행의 시간·로그 비교 | 느림이 다운로드·패키지 설치·hook 실행 중 어디인지 분류 |
| 문제 해결 | nvm 미로드, 오래된 잠금 파일, 다른 파일시스템 | 증상별 최소 확인 명령과 복구 명령 고르기 |

## 정확성·실행 위험

- Orca 문서에 없는 hook 셸·시작 디렉터리·실패 처리 동작을 단정하지 않는다. 설치된 Orca의 UI/CLI에서 확인한 범위만 쓰고 진단 명령을 제공한다.
- `.python-version`의 `3.14`와 `.nvmrc`의 `24`는 패치 버전까지 고정하지 않는다. 예제 실행 결과의 실제 패치를 기록한다.
- `uv sync --locked --offline`과 `npm ci --offline`은 미리 내려받지 않은 새 의존성에서는 실패할 수 있다. 오프라인 성공은 패키지 관리자 호출 범위에서만 해석한다.
- npm `ci`는 기존 `node_modules`를 지우므로 Orca의 복제 기능과 함께 쓸 때 속도 이득을 당연시하지 않는다.
- 같은 워크트리를 동시에 여러 에이전트가 수정하거나 하나의 설치 결과를 두 브랜치가 공유하는 흐름은 실습하지 않고 실패 조건으로 분석한다.
